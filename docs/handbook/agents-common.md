- Читать: `CLAUDE.md`, `project-design.md` (источник истины), `plan/README.md`, такс-лист своего этапа, `docs/agent-handbook.md`.
- Правила игры — в ядре `core/ZeldaDaughter.Core` (netstandard2.1, C# 9, без `UnityEngine`, `#nullable enable` первой строкой), тесты xUnit до кода, `tools/check.sh` → `CHECK OK`. Числа — в `data/*.json` с полем `_source`, не в коде.
- Unity-проект — `ZeldaDaughter/`; Unity есть только на ПК автора, через мост (`tools/pc/README.md`). Код Unity, не скомпилированный на ПК, — «не проверен», так и писать.
- Апрель (`archive/2026-04/UnityProject`) — только справочник (`docs/april-review.md`): правила, числа, тексты берём, код не переносим.
- Видимое — критерии в `docs/done-criteria/<ID>.md` до работы; «сделано» — с доказательством (тест, кадр, строка `[ZD:*]`).
- Тяжёлое (`dotnet build|test`) — под общей с The Chest блокировкой; `tools/check.sh` берёт её сам.

## Лучшие практики — до видимой работы (автор, 2026-10-08)
«Ты сам должен искать наилучшие практики в интернете, чтобы демка по итогу получилась качественной». Перед любой видимой задачей (арт, анимация, вид мира, свет, звук, ощущение управления, UX без HUD):
1. Найти, как это делают лучшие игры жанра и практики (статьи разработчиков, GDC-доклады, разборы, новые модели и инструменты), — 3–5 источников со ссылками.
2. Сравнить с текущим кадром/поведением демо и записать разрыв.
3. Делать по лучшей найденной практике, а не по первому пришедшему способу; источники и выбор — строкой в `docs/demo/decisions.md`.
Сводка исследований — `docs/demo/best-practices.md`.

## Сколько тестировать
Проверка своей правки — свои и затронутые тесты, не весь контур; полный PlayMode — только при правке общего кода, перед релизной сборкой и в интеграционном прогоне координатора. Подробно — `.claude/skills/zd-unity-bridge/SKILL.md`, «Сколько тестировать».
