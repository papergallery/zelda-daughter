# Общее для всех агентов Zelda (план 0.2, ADR-0007/0008)

- Читать: `CLAUDE.md`, `project-design.md` (источник истины), `plan/README.md`, такс-лист своего этапа, `docs/agent-handbook.md`.
- Правила игры — в ядре `core/ZeldaDaughter.Core` (netstandard2.1, C# 9, без `UnityEngine`, `#nullable enable` первой строкой), тесты xUnit до кода, `tools/check.sh` → `CHECK OK`. Числа — в `data/*.json` с полем `_source`, не в коде.
- Unity-проект — `ZeldaDaughter/`; Unity есть только на ПК автора, через мост (`tools/pc/README.md`). Код Unity, не скомпилированный на ПК, — «не проверен», так и писать.
- Апрель (`archive/2026-04/UnityProject`) — только справочник (`docs/april-review.md`): правила, числа, тексты берём, код не переносим.
- Видимое — критерии в `docs/done-criteria/<ID>.md` до работы; «сделано» — с доказательством (тест, кадр, строка `[ZD:*]`).
- Тяжёлое (`dotnet build|test`) — под общей с The Chest блокировкой; `tools/check.sh` берёт её сам.

## Сначала пилот, потом масштаб (автор и ревью процесса, 2026-10-08)
«Ты сам должен искать наилучшие практики» (автор). Перед видимой задачей — **не больше 30 мин исследования**: итог на один экран — 3 практики со ссылками, разрыв с текущим кадром, 2–3 **разных** способа. Затем **пилот** каждого способа на **одном** месте/ракурсе (≤ 45 мин и ≤ 30 ₽ на способ) с замером и склейкой «кадр | концепт». Выбор — строкой в решениях; масштабировать только победителя (образец — пилот D-25). Сводки исследований — `docs/demo/best-practices-*.md`.

## Видимое: склейка и чужой критик
- Видимая задача начинается и заканчивается **склейкой «кадр игры | концепт»**; пункт 1 критериев — «узнаётся как концепт» по осям критика (`.claude/agents/frame-critic.md`, режим сравнения). Измеримые параметры (px, число объектов) — средства, задачу не закрывают.
- **Субагент не ставит вердикт своей работе** и не ставит галочку видимой задачи: конец работы — «склейки готовы: <пути>». Критика вызывает координатор. «Оценено самим» — не доказательство.
- **Три круга ПЕРЕДЕЛАТЬ — меняем способ, не цифры** (вернуться к пилоту).
- **Свет, тени, огонь, дым, вода, свечение не рисуются в картинках** — их делает движок. Стиль — блок из `docs/demo/sprites/style-bible.md` дословно в каждом промпте.

## Границы задачи
Новое замечание к задаче в работе (от автора, координатора, исследования) не расширяет её — это новая задача `D-NNx` после текущей. Текущая доходит до коммита в прежних границах или останавливается с записью «остановлена: причина». Коммит — не реже раза в 60 мин (готовое партиями).

## Бюджет генерации
Смета — в критериях задачи; учёт — `docs/demo/budget.md` (план, факт, путь «0 ₽» на ПК). Остаток < 1,5 × сметы — путь 0 ₽ или координатор задаёт автору один вопрос о пополнении.

## Сколько тестировать
Проверка своей правки — свои и затронутые тесты, не весь контур; полный PlayMode — только при правке общего кода, перед релизной сборкой и в интеграционном прогоне координатора. Подробно — `.claude/skills/zd-unity-bridge/SKILL.md`, «Сколько тестировать».

## Ветки и коммиты (ревью процесса 2026-10-08)
- **Новая задача — свой `git worktree` и ветка `<ID>`** (`git worktree add ../zelda-wt/<ID> -b <ID>`), коммит в свою ветку не реже раза в 60 мин, `git push origin <ID>`. На ПК — `zd-sync.ps1 -ref origin/<ID>` (ставит ветку, не общее грязное дерево). В master мержит координатор после `zd-check` 0/0 по этому sha; после проверки ПК возвращается на `origin/master`.
- Пока работаешь в общем дереве (старые задачи): **коммит только с явными путями** — `git commit -m … -- <пути>`; голый `git commit` уносит чужой проиндексированный код (так D-26 уехал в коммит координатора `4489c0a9`).
